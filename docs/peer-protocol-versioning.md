# Core / Edge 通信协议版本

Core 与 Edge 共用一个整数协议版本。软件发布版本（例如 `2.0.0-preview.17`）、
厂商固件版本和协议版本各自独立。运行时只比较协议版本：相同就继续配对、重连、
路由和同步；不同则返回明确的协议不兼容错误。软件版本仍用于展示，不参与兼容判断。

## 构建时的协议指纹

`core/peer-protocol.json` 是协议版本及 SHA-256 指纹的唯一记录。`sources` 列出
参与检查的源文件或目录；构建会递归收集 Rust 文件，按仓库相对路径排序，统一
CRLF/LF，并将路径、长度和内容纳入哈希。测试目录及独立测试文件不参与收集。
为保守捕获行为变化，选中文件中的注释与内联测试也会影响指纹。

指纹覆盖 Link 编解码、配对与认证会话、空间准入和权限、同步记录及事务应用、
Core / Edge 路由和设备服务协议。另外还聚合从应用源码扫描出的完整路由目录
（binding、路由种类、生命周期、权限、创建规则和反向流类型）与路由方法签名。JSON 同步 RPC 还会收集完整方法实现，覆盖其动态字段和处理逻辑。
`schemaRoots` 还会扫描可序列化 DTO 的字段、serde 属性、类型别名及自定义编解码实现，
捕获方法签名不变但报文字段变化的情况。普通方法体变化不影响这一层结构指纹。
新协议实现文件必须加入 `sources`，不能只维护 DTO 而漏掉路由或同步行为。

Hash 仅供构建和开发检查使用，不随握手、同步请求或设备资料发送，运行时也不比较。

修改流程：

1. 修改协议相关源码，运行正常的 Cargo 构建或检查。
2. 如果指纹变化，构建会失败，并打印新的 SHA-256。
3. 在 `revisions` 末尾追加记录，将 `version` 递增并填写新 hash。历史记录保持原样。
4. 再次构建并执行 Core / Edge 互通回归。发布软件时无需再额外递增协议版本。

示例（hash 应填写构建实际给出的 64 位小写十六进制值）：

```json
"revisions": [
  { "version": 1, "hash": "<已发布的 hash>" },
  { "version": 2, "hash": "<新协议的 hash>" }
]
```

Cargo 构建检查源码指纹与当前记录一致；CI 还会将版本记录与 PR / push 的基线
比较，拒绝覆盖历史 hash、回退版本或不递增版本的修改。可在本地运行：

```sh
python3 tools/check_peer_protocol.py --base HEAD
cargo check --manifest-path core/Cargo.toml -p operit-node-runtime --no-default-features --features peer-runtime
```

## 运行时检查

- 新配对与已有凭据重连都声明协议版本；版本纳入认证 transcript。
- 空间投影协商声明同一协议版本，供 Core 与 Edge 准入及控制同步使用。
- 业务同步通过 `$node.sync` 的 `protocol` 方法读取最终目标的协议版本，适用于中继路由。
- 拓扑状态比较设备资料中的 `protocolVersion`；Edge 无需伪造 Core 软件版本。
- 协议版本不匹配返回 `PEER_PROTOCOL_MISMATCH`；缺少协议声明返回
  `PEER_PROTOCOL_UPGRADE_REQUIRED`。旧资料仍能反序列化，未声明版本显示未知，
  不会根据软件版本推断协议版本。

这是首次引入统一协议版本。此前未声明该版本的 Core 或 Edge 程序需要升级一次；
已有设备身份和配对凭据保留。此后软件版本变化、协议版本不变时，不要求厂商同步升级。
原有配对安全协议、投影分页协议和同步记录格式的内部版本继续保留，其修改也纳入总指纹。
