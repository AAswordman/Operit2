# 同步全链路第二轮优化（2026-11-16）

本轮承接 binding 时钟批量持久化和 TTS 单次快照解码，目标是复测现有千条负载、空闲文件发现及桌面真实数据到空 CLI。所有计时在 macOS ARM64、TCP loopback、隔离 CLI 进程中进行；开发构建与发行构建不能混称。

## 已有证据与本轮修改

- SQL 接收应用：上一轮 8 秒采样有 4152 个 `syncApplyOperations` 栈样本，2520 个在 SQL owner 应用路径，其中 1226 个在 `notifyInvalidated`。本轮按连续增量批次提交一次 SQLite 事务、通知一次观察者；初始化操作作为顺序边界。中途错误回滚整个增量段，保留 owner 间独立恢复。
- SQL 冲突检查：`sync_sql_versions` 主键以 `kind` 开头，实际查询按 `chatId` 限定且包含 OR 条件，原先扫描整个版本表；添加 `chatId,kind,timestamp,variantIndex` 索引，已有数据库也自动补齐。
- 操作日志：重复投递仍验证不可变摘要，但原始内容相同时不再重写 pending 记录、不再删除重建 blob 索引。完成状态、legacy 回执恢复和不同存储表示的更新仍保留。
- 配置回放：原先每条事务都深复制整个 `Data` 再发布。批量回放只保留一个回滚副本；所有操作仍按顺序验证，失败不发布中间结果。编码的版本作用域先验证，再跳过其他键的普通版本，仅解析当前键和可能影响它的记录命名空间。
- TTS 固定目录：50 次创建采样中，5887 个创建调用样本有 2028 个进入 `TtsCatalog::provider`。目录由编译期常量生成，现用 `OnceLock` 解析一次；单次查找只复制命中的服务商。
- 摘要：JSON 原有字节序列不变，增加 8 KiB 写入缓冲，减少 SHA-256 的细碎调用。CLI 补上 core/Flutter 已有的 `profile.dev.package.sha2 opt-level=2`。这是独立的开发构建设置修复，性能改善不全部归因于同步算法。
- 文件块：本机文件块直接从同一个 RuntimeFileSyncStore 读取，保留授权检查和全部块边界校验；利用现有 Link 二进制值承载上传块，避免将每个字节分配为一个整数值；接收端仍是 `Vec<u8>`，加入二进制及原整数数组解码兼容测试。
- 外部文件发现：空闲扫描退避上限从 60 秒降为 5 秒。代价是空闲时最多每分钟约 12 次元数据扫描；不把这段等待混为传输耗时。连接故障的重试退避仍遵守原来的上限。
- 无用代码：删除没有任何调用者的 `flushOperations`、旧 preference outbox 缓存字段及 `PreferencesSyncedMutation::visit`；删除只写不读的旧控制版本计数器及其 RAII 更新路径。保留实际使用的控制投影 revision、恢复流程、迁移入口和旧格式解码。
- 观测：新增接收/准备/应用/刷新、owner 应用/完成和 blob 存在性/传输阶段聚合日志，不输出业务 payload。

采样计数包含阻塞；调用栈的父子样本不能叠加成总耗时比例。同步观察器不在计时窗口内轮询 TTS 全量列表；SQL 与文件可见性仍轮询，并在排空后独立验证配置完整值、SQL 正文、文件哈希和所有 owner 的一致性摘要。

## 测试口径

`sync_backlog_session.py` 的三个阶段累计运行：先增加 1000 个不同聊天（每个 4 KiB 正文及一个 binding），再增加 300 个不同 TTS 配置，再在已有这些数据的基础上增加同样数量的聊天/配置以及 8 个 1 MiB 随机文件。另用 `--file-count 0` 直接测无文件混合场景。每阶段准备时间单独记录；drained 包含重连、显式同步、双方后续排空，验证时间另计。

blob 的 `transferMs` 包括块读取、编码、RPC、接收、哈希及落盘，不等于物理网络时间，不能直接从总时间中扣除后宣称已满足“所有本地处理低于 10 秒”。无文件负载与端到端总时间更适合验证优化目标。

桌面真实数据使用客户端 bootstrap 选定的活动身份，复制到权限 0700 的临时目录；源数据目录不被 CLI 打开为写入目录。复制保留数据库、历史、文件和插件数据；仅在副本里通过业务 API 离开原 Space，再和空 CLI 配对、加入、同步。测试进程用 sandbox 限制为两个本地端口，阻止复制的旧对端或插件访问外网。已有偏好解密密钥仅经内存写入副本私有 secret store，不在参数、终端或报告输出密钥。原数据及原 App 不参加测试连接。


## 真实数据定位后的追加修改

- RuntimeFile 使用现有 `appendOperations` 按接收页观察时钟。先持久化原始操作，再批量写时钟；完成标记仍由各 owner 成功应用后独立提交。缺失 Blob 和格式错误仍保留 pending。
- WorkspaceFile 的一页完整文件状态共用一次目录扫描，并且只物化每个路径的胜出版本。完整页预先写入 `pendingBatch` 恢复意图，逐个文件仍校验内容、刷文件及父目录，最后统一写目录清单，避免每个文件重写两遍全量清单。单文件旧恢复格式继续可读；同路径重复操作保留原有顺序路径。中途失败不会确认未应用的 owner。
- 插件 SQL 对同一 manifest 的连续操作复用已打开、已校验的数据库，初始化和 manifest 改变仍是边界。按 identity 匹配时跳过不会参与比较的本地 content 读取；插件原有事务和合并规则保留。
- 版本作用域快速跳过只用于规范 JSON 编码；恢复数据存在空白或 Unicode 转义等合法非规范编码时，回退到完整解析，避免漏掉较新的子字段与增量效果。

## Mac 活动 App 数据复制到空 CLI

源身份有 220 个聊天、867 条消息、10065 个消息片段；复制时 runtime 目录 962 个文件，逻辑大小 1,521,479,776 字节。**这不是同步传输量。** 其中模型约 1,049 MB，sync 历史约 152 MB，data 126 MB，插件数据 78 MB，缓存 72 MB，扩展 35 MB，日志 9 MB；节点本地模型和缓存不作为普通同步文件传输。

测试脚本早期将 macOS `security` 返回的十六进制密钥文本当作原始字节，导致配置被误判损坏并反复修复。该错误已修复，读取时校验密钥 JSON 信封；原 App 数据未写入。之前 67.32/69.81 秒的结果含此测试错误，不能作正常性能结论。

| 正常密钥、相同业务数据的 debug 轮次 | 加入＋完整排空 | 独立验证 |
| --- | ---: | ---: |
| 文件时钟/恢复清单批量化之前 | 53.607 s | 1.878 s |

最终这一轮接收并独立计算 SHA-256 的 Blob 为 **298 个、118,450,978 字节（约 118.45 MB）**。85 个 owner 的业务摘要一致，聊天各表行数一致，双方没有 pending/skipped/errors，原 App 源目录的大小/修改时间清单未改变。

40.696 秒这轮，接收端记录的批次阶段累计约 18.52 秒，其中应用约 15.99 秒、接收持久化约 1.72 秒、准备约 0.63 秒。4 个较大 Blob 阶段累计约 10.46 秒，其 transfer 部分含本地读取、编码、RPC、落盘和哈希，不能当成纯网络时间扣除。剩余时间还包含导出、收据/扫描及最终一致性快照；两端部分阶段重叠，不能简单累加成精确端到端分解。

**真实数据 debug 全链路尚未达到 10 秒。** 发行构建结果须单独测量并标明，不混入上述算法对比。

## 正确性检查

- 最新 focused store 回归：157 passed，1 个已有 ignored。覆盖 binding/文件时钟、SQL 批次、不可变 journal、业务契约、迁移、事务作用域、插件数据库、初始化收敛、聊天输出、统计和工作区文件。

## 按用户要求移除仅为压内存引入的策略（2026-11-16）

本轮只调整非暂存改动。撤销 V8 默认延迟编译，恢复 EagerCompile；恢复启动时准备两个引擎；恢复线程池原有轮转规则。模型目录恢复原来的初始化时机，删除为了逐条丢弃元数据而新增的自定义反序列化 visitor。删除为低内存引入的 VFS Read/Seek 适配器和插件包通用 reader 接口，注册文本资源恢复原快照接口；大文件落地恢复原字节读取接口。同步应用中仅为提前释放 payload 而新增的生命周期调整也已撤销。

保留减少重复工作的改动：首次编译直接使用得到的脚本，同一引擎复用初始化脚本编译结果；插件注册表消费旧快照而不复制；同包多个主题共享一次 archive 哈希；模型 bundle 一次解码后直接建立索引，别名索引去重、canonical 直接累计票数；JSON/事务数据转移所有权、同步页直接解码；按批更新业务与控制时钟、文件索引和父目录刷新；一次权限检查使用一份共享不可变状态，保留逐块及最终提交撤权检查；空间导出读取复用并保留有限版本重试。进度反馈与真实数据测速的内存观测继续保留，内存测试限额未放宽。
