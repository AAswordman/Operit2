# 聊天同步 SQL 扫描定位（2026-11-19）

用户反馈 iOS 与 Windows 同步三万条记录耗时一小时，对照压力测试一万条约 15 秒。本次已复现并修复当前代码中的两处随数据增长放大的 SQL 扫描；没有取得该次同步的双端版本、日志或数据，不能把一小时全部归因于这两处。

## 历史范围

先复核了 11 月 16 日的 space/backlog/chain 三份报告及现有测试。此前已经修复 SQL 连续增量按批提交、观察者按批通知、binding 时钟按批持久化、Blob 二进制载荷等问题。本次没有重复实现这些优化。

现有报告的主要基准为 macOS 同机 TCP loopback；千聊天样本每个聊天只有一条 4 KiB 消息。仓库没有找到明确对应“一万条 15 秒”的测试记录，不能擅自认定用户压力测试的输入、计时范围或覆盖链路。

## 发送端：每条候选消息扫描后续历史

`SqlChatSyncStore::operationsSinceWithBudget` 使用关联 `NOT EXISTS` 排除同实体的旧版本。已有索引只有作者/序号及创建时间，没有覆盖作者、domain、实体类型、实体 ID 和序号的索引。

实际查询计划中，外层每取一条候选，内层按作者和后续序号扫描，再过滤实体。即使每条记录都属于不同消息、无需排除任何旧版本，也会反复访问后面的历史。导出整个积压的工作量近似平方增长。

修复：在同步存储准备阶段创建仅覆盖 `entity_state` 的复合索引；已有数据库打开同步存储时也会补齐。查询、分页和压缩语义不变。新增回归验证旧库缺索引后重新打开、三万条独立实体中的旧版本淘汰，以及真实生产查询的 SQLite 执行步数上限。

## 接收端：长聊天的冲突查询扫描整个聊天

`SqlChatScopeVersions::accepts` 将消息、变体、范围删除和整聊天删除放在同一 OR 谓词中。现有复合索引只利用到 `chatId`，每次检查都扫描同一聊天的版本记录。每条消息及其片段都会调用该检查，因此总记录数相同时，集中在长聊天中的消息会比散布在短聊天中更明显地暴露问题。

修复：将各作用域拆为 `UNION ALL` 的索引查询，每个分支明确约束 kind，并按规则约束时间戳及变体。重复命中的版本不影响“是否存在较新版本”的判断。新增回归逐项比较原谓词与新查询在 144 组聊天/类型/时间戳/变体输入上的结果集合；另以三万条长聊天版本统计执行步数，防止重新引入全聊天扫描。

## 本机查询对比

环境：Windows，项目 Python venv，SQLite 3.53.1，内存数据库。使用生产查询及原索引；SQL 选页每次 256 条，连续取到空页，核对全部操作 ID。长聊天测试执行 100 次不同消息的作用域查询并核对返回修订。Rust 回归另外通过生产 native host 使用的 bundled SQLite 执行生产查询。

| 查询工作 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 导出一千条记录的全部元数据页 | 0.0619 s | 0.00180 s |
| 导出一万条记录的全部元数据页 | 6.145 s | 0.0176 s |
| 导出三万条记录的全部元数据页 | 55.706 s | 0.0551 s |
| 三万版本的单聊天，100 次冲突查询 | 0.394 s | 0.000691 s |

这些数字仅衡量 SQL 查询，不包含 payload 读取、JSON 编解码、网络、业务应用、持久化通知或最终一致性检查，也没有测 iOS 真机。修复前一万到三万的导出时间约增加九倍，证明不能只按记录数三倍推算这条路径。不能将查询加速倍数写成整轮同步加速倍数。

本次复跑脚本及原始 JSON 位于当前聊天的 `artifacts/sync_sql_lookup_benchmark.py` 和同名 `.json`。脚本读取当前生产 SQL 和 HEAD 中的旧冲突查询，只创建隔离内存数据库，不读写用户身份数据。
