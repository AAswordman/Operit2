## 修改内容

1. Flutter 窗口改为一次批量请求，不再对每行单独发请求；静态检查返回条数与消息顺序，仍按 chat/source/generation 丢弃过期结果，保留明确错误。
2. Core 每窗口只读一次消息定位列表，排序后计算每条深度。sender、participant、depth、isEdit 和文本类型选择语义保持。
3. prepare_display 接收有序上下文数组并返回等长程序数组。世界书每批读取一次规则与变量；本批相同上下文共享准备结果，相同原生程序共享编译结果。下次调用重新读取配置，无新增持久缓存。
4. 字面量模式经语法解析确认后直接使用流式字符串查找，不构建正则执行器；保留可能跨 chunk 匹配的后缀。复杂表达式仍走原有 DFA 流式匹配及捕获语义。原生替换引用解析改为直接扫描，完整消息和实时消息共用同一流式执行路径。
5. 初始历史仍使用居中的 M3 方块；已显示窗口保留正文，规则刷新不重新显示整页加载，滚动复用已准备副本。每次测量后，同一窗口连续 prepare 200 次，额外投影请求为 0；80 条窗口复用中位数约 0.004–0.007 ms/次。

## 100 ms 调度排查

之前空钩子的 109.226 ms 是 **80 次逐条投影整批** 的时间，还包含重复深度查询、请求封装、返回解码等；将其称为纯调度耗时不准确。修改后对照仍走同一实际链路，每批 80 个上下文，仅提交一次 JS 钩子。每组 7 次：

| 对照 | 整批中位数 ms | 初始 JS 排队范围 ms | 钩子 totalMs 范围 ms |
|---|---:|---:|---:|
| control_no_hook | 7.148 | — | — |
| control_noop | 12.044 | 0–0 | 2–3 |
| control_exists | 15.652 | 0–1 | 6–7 |
| control_exists_read | 16.920 | 0–1 | 7–11 |
| control_constant_1 | 16.567 | 0–0 | 3–5 |
| control_constant_10 | 36.775 | 0–1 | 15–16 |

真实世界书单规则 / 80×2 KiB 中，7 次 JS 初始排队为 0–1 ms，invokeMs 为 4 ms；整个钩子（含异步文件调用及返回）为 13–14 ms。规则和变量各读取一次，7 次合计 file_exists 14 次、read_file_full 14 次；此前单批 80 行是各 160 次。旧日志中的初始排队中位数 224 ms、最长 434 ms 来自逐条重复准备和回调积压，新链路没有复现该积压。

源码检查：NativeHostJavaScriptRuntimeHost 将任务直接发送到已有的状态队列，接收侧 recv().await 被消息唤醒；JsEngine 正常请求通过 oneshot 等待完成，异步回调主动入队推进，没有固定 100 ms 轮询。JsEngine 中 HostJavaScriptExecutionInterrupt::new(100) 属于取消后的清理时限，既不是正常调用的调度周期，也不是无条件睡眠。本轮未修改已经压力测试的传输层或 Host 调度架构。

日志是整数毫秒精度，0 ms 不代表零耗时。invokeMs 仅覆盖初始同步启动步骤，不能当作整个异步函数的纯 JS CPU 时间；钩子与整批时间也不能相加分账。
