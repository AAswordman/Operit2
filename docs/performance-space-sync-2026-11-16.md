- macOS 26.6 / arm64，Rust CLI 当前源码 **dev / unoptimized + debuginfo** 构建。
- 二进制：`apps/cli/target/debug/operit2`。
- 二进制 SHA-256：`3d78906c55d8f611b8707cc5bdd9cbc112969df4a2fae15715d7de186493cff9`。

## 当前执行路径

1. 启动、同步事务变更、连接变更、路由变化及工作区轮询触发调度。同一服务合并重复调度；每对节点共享执行锁。
2. `synchronizeOnce()` 扫描工作区、处理退场及拓扑公告。直接配对节点先交换受配对授权保护的 `snapshotHeader`，再按权限探测 `syncClockDigest`。权限边界有变化时先修复控制投影。
3. 只有没有完成基线、摘要变化、pending 或失败重试等条件成立，才进入业务 pass。可达成员在这个调度循环中逐个处理。
4. 同一对存储节点由 node ID 较小的一方协调，另一方通过 `syncRequest` 请求它执行，避免双方重复跑两份业务交换。两端日志均有 pass 记录，不应把它们简单相加当成两次传输。
5. 交换控制投影，验证 Space 与存储权限。业务包含 preferences/chat/binding/runtime_file/network_control/plugin_storage 六域；设备自己的小型偏好另行交换。
6. 每页并行取得双方完整收据与缺失事务，先补 Blob，再向两端应用合并后的原始事务；默认每次导出 512 条，同时按连接消息字节上限拆包。64 页上限只约束内层分页。
7. 导出到空页/重复页或遇到确定的业务错误后，生成双方内容 manifest，检查各自是否仍处在刚才的事务边界。内容不同、文件缺失、损坏或失败历史未覆盖时，按 owner 建立完整初始化快照修复。修复完成再采集 manifest 校验；没有修复时复用第一次 manifest。
8. 只有验证过的边界才更新 gate。运行中有新事务，调度器会接着安排一轮。

相关实现：`SpacePersistenceSyncService.rs` 的 `synchronizeOnce`、`synchronizePeer`、`synchronizeDomains`、`transferBlob`；节点 `SyncConsistency.rs`；应用 `OperitApplication::syncClock` 与 `SyncConsistency::consistencyManifest`；事务内核 `Registry::manifests`。

## 已确认可避免的问题

### Blob 字节编码放大

`transferBlob()` 调用 `toCoreValue(chunk)`，其中 chunk 是普通 `Vec<u8>`；`syncReadBlobChunk()` 也返回普通 `Vec<u8>`。Serde 将它们作为 sequence 编码，当前 ValueSerializer 为每字节生成一个 `CoreValue::Unsigned`，不是 `CoreValue::Bytes`。当前 Link 已有二进制值和从二进制值解回 Vec 的支持。

使用本轮构建的 Link 库，对 64 KiB、0..255 重复的相同 payload 做 100 次“构造值→Link 编码→解码→Vec 转换→核对相等”：

| 路径 | 一块 wire 字节数 | 100 次耗时 |
| --- | ---: | ---: |
| 当前普通 Vec 路径 | 98,309 | 1,272.047 ms |
| CoreValue::Bytes 对照路径 | 65,541 | 102.012 ms |

这证明当前路径存在可避免的逐元素编码、遍历与分配，微基准约 12.47 倍。它不是修改后端到端提速承诺：所有数字仍是 debug 库，尚未把二进制值应用到生产通道。

本机构建 `size_of::<CoreValue>() = 40`，64 KiB 变为 List 时，仅元素存储约 2.5 MiB；8 块同时持有时可达约 20 MiB，另有缓冲区和消息存储。代码中的“512 KiB”明确指原始 payload，不能当成实际内存上限。

决策：优先将 Blob 传输两端的字节载荷统一到现有二进制值机制，保留 64 KiB 分块、校验和持久化确认；改动时验证当前接收器及所支持的其他 host/peer 解码兼容。不要只增加并发掩盖编码成本。

### 空闲后外部文件发现过慢

该延迟由 2026-10-26 的明确权衡引入：2→4→8→16→32→60 秒，只有发现修改才回到 2 秒。终端/外部编辑器写入不会自行触发事务通知。

39.427 秒的 1 KiB 文件可见延迟有实测依据；它不是必须接受的网络、校验或落盘成本。但是否属于产品缺陷取决于对外部文件同步时效的约定。

决策：外部文件变化采用 watcher/脏目录通知唤醒，合并短时间连续修改，并保留低频扫描兜底。在 watcher 缺失的平台单独定义延迟上限。暂不把所有设备永久改回每 2 秒全目录扫描。

## 代码确定存在、运行影响尚未复现的缺口

`MAX_SYNC_PAGES_PER_PASS=64` 只包住内层 `for`。`synchronizeDomains()` 外层是无限 `loop`；只要最终一致性返回 false，就清除 seen、重新分页。2026-11-14 又移除了固定三轮上限。

因此 64 页不能保证单次持锁任务结束；持续写入或不断变动的 owner 可反复触发 boundary recapture。加上同一同步周期对 peer 顺序处理，慢 peer 可能延迟后续 peer。本轮静态两节点测试没有复现卡死或其他 peer 饥饿，不能把这个风险当成此次秒级文件耗时的已证实根因。

决策：给完整 pass 增加时间/工作量预算；超出后持久保留 pending、释放该 peer 执行锁并调度后续轮次。不要把超预算报成业务损坏，也不要像旧固定三次那样否定正在正常写入的数据。需要持续写入与三节点公平性的真实 CLI 回归。

## 应当保留与尚需测量的部分

- 必须保留：成员/存储授权、不可变事务身份、接收与应用分离、Blob 长度/hash 验证、写入提交、并发修改边界、纠正后的内容验证。它们保证不会把“已收原始事务”误报成“内容已正确落盘”。
- 必须具备按 owner 完整初始化的恢复能力：损坏、历史无法重放或缺失初始化不能仅靠再次交换相同增量修复。它不是健康同步每次都应支付的全量传输。
- 当前每个完整 pass 确实会遍历 owner 构造 manifest；这是一种实现方式，并非所有 owner 每次完整扫描都不可避免。后续可探索可靠的 dirty/revision 缓存，但必须覆盖迁移、外部修改和修复，不能只相信收据。
- 本轮一致性成本约 18–27 ms，文件 pass 中不足 1%，没有依据优先删它。尚未测生产大聊天库、release 二进制、移动端、真实 RTT、多跳、大 backlog 或多设备持续写入。
- 单文件远端读取路径仍是每 64 KiB 一次顺序 RPC。8 路并发作用于不同 Blob，不等于一个 Blob 有 8 块流水线。若 RTT 为 R，一个 N 块文件单是串行读请求就可能累计约 N×R；这是代码路径推断，本轮没有注入 RTT，不把它作为真实网络实测。二进制载荷优化后再决定是否实现单文件流水线/连续流。

实施顺序：**Blob 二进制载荷 → 外部文件唤醒 → pass 预算与公平性 → release/大库/有 RTT 复测后决定摘要缓存或单文件流水线。** 保留当前正确性边界和现有有效的 idle gate。
