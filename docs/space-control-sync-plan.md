# Space 控制同步加固计划

## 1. 文档范围

本文档记录 Space 控制策略同步的演进规划，源于一次真实的混合版本分叉事故：控制语义变更（`RevokeRole` 重放由"移除身份"改为"重置为默认 User"，PR #216）后，同一份控制日志在新旧构建上重放出不同的策略状态，且分叉是静默的，只能靠设备行为异常人肉发现。

本文只做规划，不描述已实现的机制。文中提到的绊线、检查点均为未来工作。

## 2. 决策基线

以下结论是本规划的前提，不在本计划内重新讨论：

1. **Space 控制面继续保持操作同步**（复制签发者绑定的命令日志 + 各节点确定性重放），不改为状态同步。理由：审计即产品（控制日志本身就是审批/移除记录）、授权在写入时点判定（重放时检查签发者当时的能力）、全序消除并发冲突（唯一管理员守卫在全序下天然安全）、离线队列天然支持（命令躺在日志里等对端回来）。状态同步在治理域会丢失审计、把授权变成对最后写入者的信任，并引入无法表达跨字段不变量的合并问题。
2. **既有命令的重放语义冻结为协议**。演化通过新增命令完成：未知命令在老节点上反序列化失败（fail-closed），好过既有命令被新语义曲解（fail-divergent，即本次事故）。语义修复型变更（如同 #216）属于例外，必须按协同升级处理：PR 附带混合版本警示，升级完成前避免对老构建设备使用新语义操作。
3. **状态是派生数据**：`状态 = f(日志, 重放代码)`。这决定了分叉的修复形态——对齐代码后重放自动收敛，不需要数据手术。

## 3. 阶段一：状态哈希绊线（检测）

在 Space 同步链路上交换校验元组，把静默分叉变成被检测的不一致。

- 交换内容：`(日志指纹, 状态哈希)`。日志指纹为对全序控制操作（`controlOperationOrder` 排序后）的链式哈希；状态哈希为 materialize 结果的哈希。可搭在现有 `PeerSpaceSnapshot`（已携带 `controlOperations`）或 space sync 握手上，加字段即可。
- 判定规则必须先区分两种情况：
  - 日志指纹不一致 → 同步落后，良性，静默追赶，不报警；
  - 日志指纹一致而状态哈希不一致 → 同日志不同重放，即真分叉（版本偏差或重放 bug），进入报警。
- 分叉处置：持久化事件（对端、时间、双方哈希），TUI 网络窗口挂醒目警告（提示升级全部设备），写日志。**不做任何自动修复动作**（见第 5 节）。
- 判定比对使用现成的 `PartialEq` 语义（`validateSpacePolicy` 已在用），实现成本低。

## 4. 阶段二：治理界面引导（呈现）

把阶段一的检测事件接到治理 UI：

- 设备管理窗口（`/network devices`）顶部横幅：与某设备策略状态不一致、疑似版本偏差、建议升级；
- 状态行在尝试对该设备执行治理动作时附带一次性提示；
- 事件在所有分叉对端升级完成、状态哈希一致后自动消除。

## 5. 明确不做

- **不静默采信对端状态**：那等于从后门引入状态同步，把"信任谁的 fold"未决问题静默处理掉；
- **不自动清理日志重放**：日志是审计与授权的权威记录；
- **不做默认的控制域整体隔离**：一台设备版本落后不应放大为整个 Space 瘫痪；警告与升级引导优先。

## 6. 阶段三（可选）：管理员检查点修复通道

当分叉需要在不升级的情况下立即收敛时，提供带信任锚的状态修复：

- admin 设备签发"第 N 条操作处的物化状态快照"（检查点，锚定日志位置）；
- 分叉节点校验签发者与管理员资格后采信检查点，再追加重放第 N 条之后的后缀操作；
- 本质是把状态同步降格为**修复机制**而非主同步模型，信任锚是 Space 治理本来就信任的管理员。

此项复杂度高，仅在阶段一、二不足以应对实际运维时启动。
