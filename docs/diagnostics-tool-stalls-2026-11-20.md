### 已实施：120 秒首字超时与现有重试

共享 `FirstOutputDeadline` 已接入 OpenAI、Claude、Gemini 的流式与非流式 HTTP 生成入口，从 `sendHttpRequest` 前开始计时，因此无需先等到响应头就能终止本次日志中的请求。有效文本、思考、工具调用或图片输出解除首字计时；响应头、心跳和元数据不解除。非流式请求计时覆盖完整 JSON 读取与解码。

超时先通过现有 HTTP Host 关闭原请求，再沿用既有重试开关、最多 5 次重试和指数退避；禁用重试或耗尽次数时明确报告终态失败。120 秒是单次尝试的上限，整轮重试没有新增累计时间预算。代理或上游持续故障时，重试仍可能全部失败，不能承诺一定返回内容。

真实 Provider 的受控 Host 回归覆盖无响应头、正文停滞、仅心跳与元数据、有效输出解除计时、重试成功、耗尽次数及主动取消。设计和验收命令见 [模型首字等待与重试](model-first-output-timeout.md)。

### 其他改进建议（尚未实施）

1. 在共享 Provider/HTTP 抽象上定义连接、响应头、首个有效 SSE 事件、流中无进展等阶段策略。通过现有 Host 执行取消，保持跨平台一致。
2. 为所有重试共享一个无响应预算，按明确的错误类别决定是否重试，避免每次尝试重新获得完整的长等待期限。保留尝试次数、原始错误与累计耗时。
3. 阶段超时应成为明确的终态错误，关闭 Host 请求、结束流、结算执行状态。沿用已有请求释放和主动取消机制。
4. 区分网络字节、SSE 心跳、有效 reasoning/content/tool-call 进展。持续输出思考或工具进展的长任务与无进展连接应使用不同规则。
5. 在界面显示当前阶段、已等待时间和重试状态。调用工具结束后等待模型续答，应展示“等待模型继续响应”，避免仍让用户以为工具在执行。
6. 给应用请求和设备上代理的上游请求加入同一关联 ID，记录代理收到请求、开始上游请求、响应头、首个事件、断开及取消时间，进一步查明 8787 服务内部的原因。

界面已经具备 `Connecting`、`Receiving`、`ExecutingTool`、`ProcessingToolResult` 等状态，`InputProcessingStatusLane.dart` 也已有对应文案。改进时应扩展现有状态链，让 Provider 的实际阶段与等待时长进入该链路；避免另建一套仅由界面计时猜测执行位置的状态。当前日志没有逐次记录用户看到的状态标签，因此尚未确认故障期间具体显示了哪一个标签。

计时、终态与错误分类应由共享 Provider 层拥有，HTTP 的打开与取消沿用 Host 抽象。重试预算由一次逻辑模型请求持有，传入各次网络尝试；阶段超时、主动取消、鉴权或参数错误分别使用明确类别，不通过匹配错误文字决定处理。流中有效进展需要在 Provider 解析 reasoning、content 和 tool-call 增量后记录，不能仅依据 HTTP 收到字节或 SSE 心跳刷新。

首字等待阈值已按用户要求确定为每次尝试 120 秒，连接与读取空闲配置继续沿用现有 Host 策略。超过约 10 秒就显示等待阶段和耗时、细分其他阶段期限等仍为后续建议。正在持续产生有效进展的推理不应仅因固定短总时长被终止。

## 2. 已复现并修复：页面异步资源上下文恢复缺口

08:48:57.085–11:06:59.224，包 `com.whatsmynames.subagent`、页面 `subagent_web` 共记录 58 次 `compose_dispatch_failed`：

其中 49 次是 `action:__action_1`，9 次是 `action:__operit_theme_changed`。Client 同时通过 FlutterDebugPrint 和结构化错误通道输出相同错误，统计时只计算结构化派发事件，避免翻倍计数。首例在日志 2011–2013 行，末例在 4693–4695 行。

该错误是页面回调执行失败，足以影响插件操作。日志未提供这些操作完整的 JS 堆栈，不能断言每个错误对应的按钮行为或页面等待状态。

修改前源码中的上下文生命周期（以下行号对应分析时的原始版本）：

1. `JsEngine.rs:1234` 在开始调用时建立包含 `textResourceSource` 的 `JsCallContext`，并安装线程本地上下文。
2. `JsEngine.rs:2536` 的 `clearThreadLocalCallState` 在执行步骤结束时清空 `CURRENT_TEXT_RESOURCE_SOURCE`。
3. `JsEngine.rs:1660` 恢复 Promise、定时器和其他异步工作前，调用 `:1131` 的 `installActiveCallContexts`，后者恢复调用表和执行 Host，但没有选择具体调用的模块资源来源。
4. `JsEngine.rs:2881` 的 `__operitNativeActivateCall` 根据调用 ID 切换中断归属，没有调用完整的 `installThreadLocalCallContext`。
5. `JsEngine.rs:2980` 读取模块时要求线程本地资源来源存在；缺少时抛出的文字与用户日志完全相同。

因此，异步回调中的模块加载存在脱离资源上下文的执行路径。该路径现已通过真实引擎测试复现；用户设备上每次报错对应的具体插件操作仍缺少完整堆栈，不能逐次断言。

JS 侧 `JsInitRuntime.script.js:249` 在设置 `__operitCurrentCallId` 时已经调用原生的激活入口，Promise 续体也按订阅者恢复该 ID。修复应在这个已有的原生激活边界按精确 ID 选取 `JsCallContext`，统一恢复调用能力；逐个修改插件中的 `require` 无法修复共享引擎的上下文归属缺口。现有同步模块读取测试未跨越 Host 等待和下一次引擎执行步骤，不能覆盖本次缺口。

### 已实施的修复

- 原生激活入口按准确调用 ID 同步选择完整 `JsCallContext` 与取消预算；删除 Host、资源、环境与回调的重复线程本地状态。
- 当前能力与活动调用注册表分别管理；空或未知身份不获得能力，其他调用的记录仍然保留。
- 模块读取使用调用捕获的资源来源，挂起页面动作在并发重渲染后继续使用原快照；后台工作保留自身包资源。
- 嵌套作用域成对恢复上下文、注册表和注册参数；终态处理及有界取消清理完成后才释放作用域。
- JS 订阅清理先恢复被清理调用的身份，异常时仍移除会话、清理定时器并恢复存活调用。

新增 8 项原生引擎用例已全部通过，覆盖调用能力隔离、嵌套恢复、Host 等待与并发渲染、定时器、主题 effect、WebView 异步回调、后台 Promise 与取消清理。相关 JS 生命周期和共享传输测试 50 项通过。原生桥接库扩展回归 155 项通过，4 项手动性能测试忽略，1 项已在修改前复现的角色卡 fixture 失败单独排除。扩展 Node 测试另有两项既有 fixture 失败，亦已通过原始版本对照确认。

Commit 追溯、完整生命周期、命令和验收边界见 [JS 调用上下文归属](js-call-context.md)。后续仍需在 Android 上复测原始子代理插件，并补齐动作、模块路径与错误堆栈的诊断关联。

### 第一批：前台可靠性

1. JS 异步资源上下文归属的共享实现与回归已完成；仍需 Android 原始插件复测。

4. 让界面显示执行工具、等待模型、接收输出、重试、失败各阶段，等待和取消都可观察。

### 第二批：诊断能力与其他长等待

1. 让提交、模型请求、工具调用、Host 请求和界面动作共享可追踪的关联 ID。
2. 工具日志记录排队、钩子、权限、Host/远程执行、返回、终态及业务成功与否；为每次调用记录唯一 ID、所属对话轮次和执行策略，完成时记录成功与失败结果数量。订阅读取要标记为订阅等待。
3. 对长时间无进展输出稀疏诊断事件，记录所在阶段和最后进展时间。保留故障前后的 Core/Client 对齐记录，减少依赖大量 V6 调试日志。
4. 另行复现聊天切换、Host 通知及下载异常，分别确认其拥有者和阻塞点。

建议将工具执行、模型传输和页面动作的稳定性分开度量：分别统计分阶段 P95/P99、无进展时长、失败率、取消完成时长与取消后仍存活的请求数。目标应同时覆盖“异常等待有明确终态”和“有效长任务可持续执行”。先用无响应头、只有心跳、跨异步模块加载等受控故障验证，再在 Android 实机上核对前后台切换、页面并发与取消后的下一轮对话。

| 场景 | 预期结果 |
| --- | --- |

| 页面操作并发、主题变化、关闭或取消 | 上下文归属正确，各动作互不污染，资源正确释放 |
