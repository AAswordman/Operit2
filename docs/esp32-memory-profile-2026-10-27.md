# ESP32 模拟器 Rust 堆分配实测（2026-10-27）

这份报告按真实分配/释放记录给出字节数。分项统计对应同一次总堆峰值，所有分项互斥且可以与分配器总账核对。

## 测量条件

- 运行完整 `simulator-space.test.mjs`，覆盖配对审批、聊天、插件调用、断线重连、90 行历史分页、取消及进程重启。
- Rust 堆固定 262,144 字节，仍使用原来的 `linked_list_allocator`。每次分配记录请求大小、实际 `heap.used()` 增量、指针及调用栈；释放时撤销原始分配。
- 总占用刷新峰值时，复制当时仍存活的分配计数。表中的峰值是同一时刻的占用，未累加各模块在不同时刻的最大值。
- 调用栈地址使用本轮匹配的 EXE/PDB 离线解析。按分配点向上的第一个项目源码帧分类；这表示直接分配来源，跨模块传递后的对象所有权需要另行分析。
- 诊断表位于独立静态区，写文件直接调用系统 API，未从设备堆分配统计元数据。统计区、诊断工具自身和线程栈均不计入下表。
- Windows 调用栈采样会增加执行栈消耗，诊断运行临时使用 64 KiB 的主/异步/阻塞栈。此表属于该诊断运行。随后已逐字节恢复源码和测试断言，在原有 16/24/20 KiB 栈限制下复验完整场景。
- 本轮启用 release 行号调试信息，优化级别仍为 3。结果属于 Windows 模拟器的 Rust 堆，不能直接当作真机整板 RAM。

## 恢复严格预算后的复验

恢复主栈 **16 KiB**、异步栈 **24 KiB**、阻塞栈 **20 KiB**，移除本轮所有临时分配钩子，再次执行完整集成场景：**1/1 PASS**，堆历史峰值 **249,168 / 262,144 字节**，所有采样的分配失败数为 0。两轮的异步调度时序及测量条件有差异，分项表仅对应上面的 252,208 字节诊断运行。

## 本地原始证据

文件保存在 `tools/esp32-editor/generated/memory-profile-20261027/`（generated 目录被 Git 忽略）：

- `allocation-breakdown.json`：完整分类、每个分配来源的峰值/实时计费、请求大小、数量及符号化调用栈。
- `assistance2-heap-49724.bin`：本轮最高峰进程的原始分配汇总。另两份 bin 属于场景重启后的进程。
- `assistance2-heap-stacks.txt`：按峰值字节数排序的完整调用栈。
- `operit-esp32-simulator.exe`、`operit_esp32_simulator.pdb`：与原始栈地址匹配的测量程序和符号。
- `assistance2-analyze-heap.py`：离线解析及核对程序，使用本目录的原始数据与程序文件。
- `heap_profile.rs`、`instrumentation.patch`：本轮临时采样代码和相对测量前源码的改动，未保留在运行代码中。
- `assistance2-heap-profile-integration.log`、`strict-recheck.log`：诊断运行和严格预算复验日志。

可重新核对原始分配和符号：

```powershell
.venv/Scripts/python.exe -X utf8 tools/esp32-editor/generated/memory-profile-20261027/assistance2-analyze-heap.py
```

测量结果表明，后续应分别处理队列块的固定成本、Host 描述数据的重复持有、界面快照产生的临时对象，以及模拟器自身的 IPC 开销。聊天重复表示只是其中一部分。
