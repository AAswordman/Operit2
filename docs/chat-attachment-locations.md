# 聊天附件的位置与生命周期

普通文件、粘贴图片按所属聊天保存在实际导入节点的
`runtime/data/chat_attachments/<chatId>/<attachmentId>/<原文件名>` 中，重启后仍可读取。
这里的 `runtime` 是当前身份的运行时根，不是跨身份共享目录。该目录为 `CoreNode`
所有：设备本地持久化，不加入 Space 持久化文件同步，也不参与启动清理。

上传阶段使用 `runtime/temp/clean_on_exit/chat_attachment_uploads/<uploadId>/<原文件名>`。
长度校验通过且聊天仍为请求时选择的聊天后，Host 将文件移动到正式附件目录，不再额外
复制文件。取消或登记失败时清理该上传目录；进程中断留下的上传由现有启动清理回收。
普通文件、粘贴图片和插件提交的上传都必须归属于一个已存在的聊天。

正式附件每个独占一个目录，保留原文件名；同名附件由独立 ID 隔离。清理时可以按
聊天目录定位，也可以按附件目录定位，但必须先确认没有消息变体、聊天分支或待发队列
继续引用。聊天分支会复用原消息中的附件地址，因此删除聊天、移除输入附件和发送后
清空输入都不会直接递归删除正式附件。本次调整不加入引用回收器，也不迁移旧文件。
`runtime/temp/clean_on_exit` 中的截图、语音等其他工具临时产物维持原有清理规则。

- `AttachmentInfo.nodeId` 记录文件实际所在节点，在文件导入时读取本机已有身份；
  不在消息发送或接收时覆盖为当前执行节点，不新建节点身份。
- 原 `filePath` 保留，供本机预览和直接媒体读取。发送给 AI 的附件标签携带
  `node_id`，并通过 `path` 提供附件目录的 VFS 地址
  `/app/data/data/chat_attachments/<chatId>/<attachmentId>/<原文件名>`。
  VFS 的 `/app/data` 映射整个 Runtime 根，因此这里包含两层 `data`。
- 文件位于另一节点时，不能通过当前节点的文件 Host 或媒体池读取。远端图片、音频、
  视频回退成带来源信息的附件标签，不因错误的本地媒体读取而中断发送。
- AI 可以直接使用已内嵌内容；确需读取原文件时，先检查节点可达性，再使用
  `switch_core` 在来源节点继续执行。此操作改变聊天执行节点，不是远程文件读取。
- 来源离线时，需要明确提示重连或重新上传，不搜索其他设备的目录。旧消息引用的
  `/app/data/temp/clean_on_exit` 附件文件在历史版本中已被启动清理删除，无法恢复，
  同样提示重新上传。
- 旧消息和旧附件没有节点信息时保持来源未知，不伪造来源。文本、通知、位置、包信息和
  `@工作区` 等内嵌附件不需要为了读取已附带内容切换节点。

这里同步的是聊天中的位置元数据，不是附件字节。需要多端共享的文件，应实际复制到
工作区本体；工作区同步边界见 `workspace-file-sync.md`。

## 文件选择与流式导入

- Android 聊天选择器只返回平台持有的输入 token、文件名、MIME 类型和可选大小；
  不读取整文件、不返回文件字节，也不把客户端 URI 当成 Runtime 的文件路径。
- Web 选择器保留浏览器原始 `File/Blob`，只在读取时对最多 1 MiB 的切片调用
  `arrayBuffer`，不把整个 Blob 转成 Dart 字节数组，也不按块重复获取整个 object URL。
- OpenHarmony 选择器只返回 URI 和元数据，原协议的 `bytes` 字段已删除；读取时
  延迟打开原生描述符，以最多 1 MiB 异步读取，结束、取消、失败或插件解绑时关闭。
  选择文件本身不再复制到缓存目录。
- iOS、macOS、Windows、Linux 使用文件源的范围读取，不在 Dart 中预读整文件。
  拍照附件同样进入共享输入链路，仅为识别 MIME 读取最多 32 字节文件头。
- 聊天和快照共用 `SelectedFileInput` 的有界读取能力。每块最多 1 MiB，
  上传方等待当前块写入后再读取下一块；Android 元数据查询和读取均在后台线程执行。
- 普通附件通过 `AttachmentTransferManager` 的 reverse stream 直接写入接收 Host 的
  `RuntimeStorageWriteSession` 暂存。校验长度后提交，再附着到聊天并移动到正式目录，不再通过
  `transferred_file:` 或整文件 Base64/JSON 导入，也不额外复制一份归档。
- 文件大小未知时按流实际接收的字节数校验；空文件同样提交为零字节文件。
- 失败、取消或聊天切换时关闭输入并清理未附着的上传。只有成功提交的文件才可附着，
  文件的 `nodeId` 从实际接收 Host 已有身份读取。

## 消息区附件展示

附件标签既承载真实文件，也承载已经内嵌的上下文；展示方式不能只看扩展名，
也不能只对某个插件名做特殊处理。气泡与命令行聊天共用以下规则：

| 内容 | 默认展示 | 查看方式 |
| --- | --- | --- |
| 插件注入的内嵌文本/JSON/XML、时间天气等设备信息、通知、位置、屏幕文字、粘贴文本 | 消息底部的低对比“补充信息”入口，点开查看 | 点击查看完整可选择文本，并可复制 |
| 工具包、技能与 `@工作区` 引用的内嵌内容 | 同一补充信息入口，详情保留包名或引用路径 | 同上 |
| 文档、代码文件、压缩包及其他真实文件 | 保持原来的 72×72 文件缩略卡与气泡堆叠展示 | 点击进入文件预览 |
| 图片 | 保持原来的缩略图与气泡堆叠展示 | 点击图片缩放预览 |
| 音频、视频 | 保持原来的媒体附件卡片 | 点击播放预览 |

客户端以 MIME、媒体池类型、文件来源和内嵌内容共同判断：有非空内嵌文本、
文本/结构化文本 MIME 且使用合成 ID 的附件按上下文展示；有真实路径或媒体池来源
的附件仍按文件/媒体展示。`workspace_mention:` 和 `package_attach:` 是内嵌引用，
即使后缀包含路径也使用紧凑展示。插件通过现有 `type: text` 选择器结果提交的信息
自然适用此规则，通过已提交上传返回的 `type: file` 则保持文件展示，无需逐插件适配。
已有 `workspace_context` 系统上下文仍由消息解析器隐藏，不新增可见卡片。
真实文件和媒体卡片的尺寸、样式及堆叠交互保持原样。
内嵌上下文不进入附件区、不参与卡片堆叠；只在消息正文下方显示一个无底色、无边框、
无图标的低对比“补充信息”入口，常规字号下高度约 14。数量增加只更新计数，
不增加默认占用；点击后才显示各项详情及复制操作。

这只改变消息区展示与查看交互，不改变附件标签、注入正文、发给模型的内容或持久化位置。
