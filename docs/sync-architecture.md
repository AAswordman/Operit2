# Space 持久化同步

同一 Space 内，具备 `storage.provide` 且提供 Core 存储服务的节点交换持久化操作与 Blob。配对、成员资格、路由可达性和存储授权分别校验；Edge 的控制状态边界见 [Edge 架构](edge-architecture.md)。

## 职责与数据路径

```text
本地业务变更 -> 数据集原子提交 -> 持久 outbox -> 操作日志
                                                     |
                                             Router / PeerSync
                                                     |
原始操作与接收凭据 -> 数据集解码与重放计划 -> 原子提交 -> 通知
```

| 组件 | 职责 |
| --- | --- |
| `SpacePersistenceSyncService` | 授权、交换、分页、Blob 与调度 |
| `SyncOperationStore` | 原始操作、身份指纹、接收凭据与日志查询 |
| `PreferenceMerge` | 偏好 owner 声明与物化协调 |
| `PreferencesDataStore` | 单数据集工作副本与原子提交 |
| 各业务 owner | 历史编码转换、业务验证与提交后运行时更新 |

一次接收与一次业务应用是不同事实。操作可靠保存后才能推进接收凭据；业务提交完成后才能标记已应用。相同操作身份必须携带相同内容，重复投递幂等，内容冲突明确报错。

每个偏好文件是独立数据集。一个数据集失败不能阻止独立数据集提交；普通稳定引用不组成跨文件事务。跨文件业务操作不具备单次原子性。

## 版本与重放语义

本地存储 schema、逻辑操作契约版本和因果/来源顺序分别表达，互不替代。本地 schema 升级只转换存储表示，不能据此丢弃历史操作或生成覆盖全部业务历史的快照。已发布编码由对应 owner 显式解释，普通字符串保持原类型。

偏好操作包含完整赋值、完整删除、整数增量和字段修改。有效重放计划按确定的操作顺序计算：

- 完整赋值或删除重置同一根条目此前的效果。
- 随后的字段修改和整数增量继续生效，并满足实际依赖。
- 同一原始事务中的其他根条目独立计算，仍在同一次数据集提交中发布。
- 原始操作身份、内容和归档记录完整保留；计算计划不改写历史。

例如，早期 `provider.name = old` 被后来的 `provider = snapshot` 覆盖，只需从该完整赋值重建 provider。该早期事务中独立的 `counter += 2` 仍执行一次。有效操作依赖缺失时，整个数据集工作副本不提交。

实体身份合并只执行已明确记录的决定。引用投影使用目标数据集已经提交的身份决定；传输分页或分块结束不能授予业务合并许可。

偏好布局由节点本地的 `PreferenceLayout` 管理，直接复用 DataStore 的 `withSchema` 执行逐版本迁移。单文件 schema 管理文件内表示，布局 schema 管理文件的创建、设置所有权转移和旧路径退役。迁移步骤必须可重入：先提交目标数据，再登记退役路径，最后由 DataStore 原子提交布局版本与退役声明。跨文件迁移不宣称具有跨文件原子性；失败时布局版本不推进，同步保留原待处理操作。

同步在布局准备成功后继续执行既有的文件版本约束。现用偏好统一通过业务 owner 的 DataStore 创建方法完成本地初始化，不重复声明版本或用解码器代替本地迁移。退役意味着旧来源不再拥有设置写入权；其迟到操作仅在原文归档成功后完成接收，不重建旧文件或覆盖当前实体。退役历史不参与现用数据集的投影。布局状态只属于本节点，不参与 Space 同步，也不能由远端版本推进。

## 提交与 outbox

偏好业务值和内部 `__operit_preferences_replication` 字段经 Host 原子写入一起提交。内部字段保存初始值导入标记、来源 epoch/序号、逻辑时间、已应用指纹及待归档 outbox，对外业务序列化不暴露它。

业务提交后归档原始操作，归档可靠完成后清除 outbox。归档失败保留同一操作供后续发布；业务提交失败不能产生可导出的操作。`runtime/sync/preference_outboxes.json` 只登记位置与加密策略，登记记录不代表业务提交成功。

数据集锁覆盖历史收集、归档与 outbox 合并、解码、重放和提交。SQL 数据集使用其现有事务；具体同步应用记录与业务状态必须遵守该 owner 的提交边界。

## 日志读取与内存边界

`SyncOperationJournal` 通过 Host 范围读取扫描 JSONL，使用 64 KiB 缓冲与不持有业务 payload 的轻量索引。`SyncOperationStore::readJournal` 统一处理导出、合并声明与 owner 历史查询。

收据、domain、数据集和水位先筛选；调用者过滤先于实体状态压缩。偏好历史与事务不进行实体状态压缩。需要检查 payload 的记录逐条解码，页面按精确序列化字节数与记录数限制；单条超限记录由传输层处理。

归档和待应用记录在同一查询规划器内去重、排序与分页，应用层不能在分页之后追加完整待应用队列。全局注册表持有弱引用；最后一个 Store owner 释放后，共享索引、账本和 Host 可以释放。锁顺序为接收账本在前、按设备顺序的日志锁在后。

轻量索引仍随记录数增长。单条超大记录、完整历史请求和数据集合并工作集仍有对应内存成本；偏好回放不能按任意页面截断跨操作依赖。

## 待应用记录

`receive_state.json` 的 `formatVersion: 2` 保存收据、指纹与轻量元数据，payload 位于 `pending/<sha256(opId)>.json`。加密偏好继续按其加密编码持久化。

接收时先原子发布记录文件，再提交引用与收据账本。应用完成时先提交移除引用的账本，再删除记录文件；加载时清理私有目录中未被引用的文件。

旧内嵌格式逐条迁出并保留原始编码，所有记录文件落盘后才原子替换账本。升级中断时，原账本和原始操作仍是重试依据。
