# Space 持久化同步

同一 Space 内，具备 `storage.provide` 且提供 Core 存储服务的节点交换持久化操作与 Blob。配对、成员资格、路由可达性和存储授权分别校验；Edge 的控制状态边界见 [Edge 架构](edge-architecture.md)。

## 职责与数据路径

```text
本地业务变更 -> 数据集原子提交 -> 持久 outbox -> 操作日志
                                                     |
                                             Router / PeerSync
                                                     |
原始操作与接收凭据 -> 数据集解码与重放计划 -> 原子提交 -> 通知
```

| 组件 | 职责 |
| --- | --- |
| `SpacePersistenceSyncService` | 授权、交换、分页、Blob 与调度 |
| `SyncOperationStore` | 原始操作、身份指纹、接收凭据与日志查询 |
| `PreferenceMerge` | 偏好 owner 声明与物化协调 |
| `PreferencesDataStore` | 单数据集工作副本与原子提交 |
| 各业务 owner | 历史编码转换、业务验证与提交后运行时更新 |

一次接收与一次业务应用是不同事实。操作可靠保存后才能推进接收凭据；业务提交完成后才能标记已应用。相同操作身份必须携带相同内容，重复投递幂等，内容冲突明确报错。

每个偏好文件是独立数据集。一个数据集失败不能阻止独立数据集提交；普通稳定引用不组成跨文件事务。跨文件业务操作不具备单次原子性。

## 版本与重放语义

本地存储 schema、逻辑操作契约版本和因果/来源顺序分别表达，互不替代。本地 schema 升级只转换存储表示，不能据此丢弃历史操作或生成覆盖全部业务历史的快照。已发布编码由对应 owner 显式解释，普通字符串保持原类型。

偏好操作包含完整赋值、完整删除、整数增量和字段修改。有效重放计划按确定的操作顺序计算：

- 完整赋值或删除重置同一根条目此前的效果。
- 随后的字段修改和整数增量继续生效，并满足实际依赖。
- 同一原始事务中的其他根条目独立计算，仍在同一次数据集提交中发布。
- 原始操作身份、内容和归档记录完整保留；计算计划不改写历史。

例如，早期 `provider.name = old` 被后来的 `provider = snapshot` 覆盖，只需从该完整赋值重建 provider。该早期事务中独立的 `counter += 2` 仍执行一次。有效操作依赖缺失时，整个数据集工作副本不提交。

实体身份合并只执行已明确记录的决定。引用投影使用目标数据集已经提交的身份决定；传输分页或分块结束不能授予业务合并许可。

偏好布局由节点本地的 `PreferenceLayout` 管理，直接复用 DataStore 的 `withSchema` 执行逐版本迁移。单文件 schema 管理文件内表示，布局 schema 管理文件的创建、设置所有权转移和旧路径退役。迁移步骤必须可重入：先提交目标数据，再登记退役路径，最后由 DataStore 原子提交布局版本与退役声明。跨文件迁移不宣称具有跨文件原子性；失败时布局版本不推进，同步保留原待处理操作。

同步在布局准备成功后继续执行既有的文件版本约束。现用偏好统一通过业务 owner 的 DataStore 创建方法完成本地初始化，不重复声明版本或用解码器代替本地迁移。退役意味着旧来源不再拥有设置写入权；其迟到操作仅在原文归档成功后完成接收，不重建旧文件或覆盖当前实体。退役历史不参与现用数据集的投影。布局状态只属于本节点，不参与 Space 同步，也不能由远端版本推进。

## 提交与 outbox

偏好业务值和内部 `__operit_preferences_replication` 字段经 Host 原子写入一起提交。内部字段保存初始值导入标记、来源 epoch/序号、逻辑时间、已应用指纹及待归档 outbox，对外业务序列化不暴露它。

业务提交后归档原始操作，归档可靠完成后清除 outbox。归档失败保留同一操作供后续发布；业务提交失败不能产生可导出的操作。`runtime/sync/preference_outboxes.json` 只登记位置与加密策略，登记记录不代表业务提交成功。

数据集锁覆盖历史收集、归档与 outbox 合并、解码、重放和提交。SQL 数据集使用其现有事务；具体同步应用记录与业务状态必须遵守该 owner 的提交边界。

整段会话删除使用保留的 SQL 事务操作，历史行删除、删除事实与接收凭据在同一事务提交。
删除事实沿用 `sync_sql_deletions`，不依赖 Space 成员或 Binding。对同一会话 ID，删除是
终态而非可被后续 upsert 撤销的普通字段；迟到写入仍保留原始操作并推进接收凭据，但不
重建会话或子记录。同一操作中的其他会话正常应用。退出后删除、重新加入也遵守此规则。
同步提交后通过 Host 调度器停止该会话的本地执行并清理界面，不另建删除 RPC。
数据库 28 → 29 为删除事实建立查询索引，并在同一升级事务内清除旧链路已删除却又被
恢复的会话行；原始操作和删除记录保留，失败不推进版本。
启动恢复当前会话时，仅在选中的 ID 不存在时按该 ID 查询删除事实；确认已删除才清空
持久化选择。其他缺失仍报错，不扫描会话列表或重放同步日志。

## 日志读取与内存边界

生产日志位于 `transactions.sqlite`；聊天和插件 SQL 通过同一 source 接口导出各自的业务日志。SQL 元数据索引先规划页面，再读取选中的载荷。旧 JSONL 与接收文件仅由兼容导入器读取。

收据、domain、数据集和水位先筛选；调用者过滤先于实体状态压缩。偏好历史与事务不进行实体状态压缩。需要检查 payload 的记录逐条解码，页面按精确序列化字节数与记录数限制；单条超限记录由传输层处理。

归档和待应用记录在同一查询规划器内去重、排序与分页，应用层不能在分页之后追加完整待应用队列。全局注册表持有弱引用；最后一个 Store owner 释放后，共享索引、账本和 Host 可以释放。锁顺序为接收账本在前、按设备顺序的日志锁在后。

轻量索引仍随记录数增长。单条超大记录、完整历史请求和数据集合并工作集仍有对应内存成本；偏好回放不能按任意页面截断跨操作依赖。

## 待应用记录

`receive_state.json` 的 `formatVersion: 2` 保存收据、指纹与轻量元数据，payload 位于 `pending/<sha256(opId)>.json`。加密偏好继续按其加密编码持久化。

接收时先原子发布记录文件，再提交引用与收据账本。应用完成时先提交移除引用的账本，再删除记录文件；加载时清理私有目录中未被引用的文件。

旧内嵌格式逐条迁出并保留原始编码，所有记录文件落盘后才原子替换账本。升级中断时，原账本和原始操作仍是重试依据。

## 一致性比较的业务边界

SQL 完整快照仍携带所有表列和原始覆盖凭据，用于条件导出、修复与提交校验。一致性清单只使用 `digest` 判断内容是否相同，由数据所属模块排除本地辅助信息后计算，不设置旧摘要回退或兼容字段。所有同步设备需一起更新；新旧版本混用会因摘要规则不同继续触发完整快照修复。

聊天 owner 比较时排除 SQLite 本地分配的 `messages.messageId` 和 `message_variants.variantId`，按去掉本地列后的内容重新排序。消息正文、业务标识、消息部件、版本事实等仍参与比较。插件 owner 排除对象存储的本地 CAS `version`；身份映射忽略记录映射的来源及“自身到自身”的无效映射，相同有效映射去重，真正的别名决定和业务值仍参与比较。完整快照 token 不做这些投影，因此本地行号或 CAS token 改变仍会阻止使用过期快照覆盖。

## 同步触发诊断

运行日志按以下事件串联同步原因：

- `sync_cycle.start triggers=...`：本轮合并的唤醒来源，包括服务启动、同步数据变更、连接变化、加入 Space、工作区扫描和上一轮运行期间的新变更。周期开始不表示执行了全量快照传输。
- `sync_gate.required reasons=...`：进入对端同步流程的条件，包括首次建立基线、本地状态变化、远端时钟变化、待处理工作、失败重试或仅交换授权。
- `sync_pass.start/done/failed`：目标节点、调用来源、排队与执行耗时、待处理状态及失败后的重试时间。路由切换的来源包含 `route_change` 和会话 ID。
- `sync_consistency.correct mode=full_snapshot`：决定进行完整文件快照修复，INFO 级别记录 `reason=content_digest_mismatch/local_file_missing/remote_file_missing`、文件路径、两端内容摘要和逻辑版本、选定的数据来源。
- `sync_consistency.snapshot/applied/deferred/done`：快照或覆盖凭据大小、应用结果、并发修改导致的延后和最终一致性结果。`coverageOnly=true` 表示覆盖凭据；`bytes` 是导出的 Blob 大小，已持有的 Blob 不会重复传输。

定位重复全量时先搜索 `mode=full_snapshot`，再按目标节点和时间对照 gate 与周期来源。关键快照决策及结果使用 INFO；空闲轮询来源保留在 V5 周期日志中。

## 应用失败与矫正

临时失败保留 pending，等待连接、锁或文件状态变化后重试。确定的能力／数据失败记录日志，将该文件未应用事务标记为 skip；后续同文件增量直接 skip，原文和原始顺序继续参与转发，不进入 pending 阻塞集合。整批失败不再拆成逐条重复应用。未知错误保留重试，避免误判基础设施故障。

矫正携带双方当次捕获的 skip ID，与文件覆盖范围一起写入初始化事务，然后清理对应旧原文。内容已经相同但仍有 skip 时也完成封存；导出后新到的事务保留到下一轮。缺少业务 owner 的 Space preference 可通过文件适配器恢复，临时 pending、权限与并发文件修改检查继续生效。双方需支持协议 5。

## 事务合并

Preference 同步先按身份并集、定位并迁移到共同表示，再用公共 `Transaction::compaction` 选择有效事务，最后重放。合并结果中的删除 ID 随文件提交意图持久化，SQL 提交只执行这份清单，保留身份指纹和收据。本地编辑复用相同合并函数，只查询当前格式的普通历史，不读取初始化载荷。聊天和插件 SQL 继续在同库提交内维护范围索引。普通合并要求独立赋值及上下文无关的迁移；原子事务仍有部分效果有效时整笔保留，声明、增量、层级范围和业务 merge rule 保留原文。

强制矫正是 [事务模型](transaction-model.md) 中的故障恢复规则：两端保存同一条完整初始化事务，删除该 owner 已封存的旧日志。初始化保留业务修订、范围版本、删除事实、别名和精确覆盖身份，接替旧独立基线。离线节点安装初始化后重放其未覆盖修改，空节点直接恢复完整文件。

初始化事务参加正常分页、收据和转发；较大的内容使用现有校验 Blob 传输。收据、覆盖判断和导出规划只查询 SQL 元数据；普通写入不解析初始化快照。同步协议版本为 5，两端在交换前确认支持初始化事务。
