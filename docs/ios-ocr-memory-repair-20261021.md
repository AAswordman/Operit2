# iOS OCR 内存峰值控制（2026-10-21）

## 故障依据

`testflight_feedback-14.zip`（2.0.0 build 18）中，读取图片触发 AppleRuntimeChannel 的 OCR 调用。Vision 内部 TextRecognition 工作线程在创建文字检测中间结果时触发 `__throw_bad_alloc_shim`，经 C++ terminate 结束进程。附件没有原图、像素尺寸或分配大小，不能断言图片过大就是唯一原因，也不能据此确定存在内存泄漏。

旧入口将文件 URL 直接交给 `.accurate` 的 VNRecognizeTextRequest，不限制原始解码规模或 Vision 输入规模。这次修复在调用系统识别之前控制输入与内存余量；不尝试在调用线程捕获其他系统工作线程上的 C++ 分配异常。

## 修改

新增 `ios/Runner/AppleTextRecognizer.swift`，并将其登记到 iOS Runner 构建目标。AppleRuntimeChannel 的识别入口委托该实现，保持现有成功响应 `{"text": ...}` 和 `OWNER_SYSTEM_RECOGNIZE_TEXT_ERROR` 错误通道。

- 先检查文件元数据，接受非空普通图片文件，文件上限 64 MiB、源图上限 6400 万像素、单边上限 65535 像素。
- ImageIO 读取元数据时禁用原图缓存，再通过受限 thumbnail 解码；不先创建全尺寸 UIImage 或修改原文件。
- 送入 Vision 的图片最长边不超过 2048、总像素不超过 300 万；内存余量不足时进一步缩小。小图不放大，EXIF 旋转/镜像在解码阶段应用，保留宽高比。
- 通过 `os_proc_available_memory()` 检查本进程可用内存：预留 128 MiB，并为潜在原图解码工作缓冲按每源像素 8 字节预留余量；Vision 输入按每像素 128 字节估计工作空间。它们是保守准入估算，并非 Apple 私有实现的内存上限。
- 解码后再检查一次余量；像素预算不足 512×512 时提前返回错误。零可用内存同样拒绝，不绕过限制。
- 识别全程由共享锁串行化，不同实例不能同时运行；显式 autoreleasepool 在解锁前释放临时解码和 Vision 对象。异常返回路径也释放锁。
- 继续使用 `.accurate` 识别，返回纯文字；记录实际缩图尺寸，便于新版反馈定位。

对于被拒绝的源图，调用者会得到错误。大图缩小可能降低细小文字的识别率；不允许为了识别质量绕过内存准入。

## 验证

```sh
ruby tools/tests/run_ios_ocr_tests.rb
```

脚本生成临时 UIKit 测试宿主，直接编译生产 AppleTextRecognizer，调用真实 ImageIO 和 Vision，无需构建 Rust/runtime 资源。可传 simulator UDID；完整日志和 xcresult 保存到输出目录。

11 项 XCTest 覆盖：

1. 8000×6000 JPEG 解码为 2000×1500，符合最长边与总像素上限。
2. 六个并发请求的内存密集区段不交错，失败后锁正常释放。
3. 极端源图尺寸在解码前拒绝。
4. 低内存时拒绝进入 Vision。
5. 解码后内存下降时再次拒绝。
6. 文件缺失、损坏、空文件、过大文件和目录返回错误。
7. JPEG、PNG 均检查源图解码工作空间；余量足够的 PNG 可缩图。
8. 较少内存余量时进一步降低目标像素数，维持宽高比。
9. 4000×2000 文字图片缩为 2048×1024 后，由真实 Vision 连续两次识别到 OPERIT 与 12345。
10. 小图不放大，EXIF 方向 6 正确旋转。
11. 零内存余量不能绕过准入。

内存边界测试使用注入的可用内存数值，识别本身调用真实 Vision。测试宿主在当前模拟器中用系统接口得到零余量，因此实际识别测试也使用明确的注入预算，不能当作真机进程内存读数验证。

iPhoneOS arm64、iOS 16.4 最低部署目标的生产 OCR 源码类型检查通过。尚未在反馈对应真机复现；没有原始故障图片，不能宣称验证了同一张图。系统内存还受其他并行任务和私有框架影响，准入和缩图降低风险，不提供对所有系统内存故障的保证。尚未打包或发布 TestFlight。
