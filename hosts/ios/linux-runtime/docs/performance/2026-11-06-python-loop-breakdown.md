# 2026-11-06：原始 Python 循环约 2,000 ms 的来源

> 历史记录：本页测量对应已删除的 C++ region/kernel 后端。当前执行器与结果见 [静态汇编执行器](../static-execution.md) 和 [交付状态](../delivery-status.md)。

本轮仅分析时间来源，没有修改生产执行器，也没有继续做性能优化。全部运行限于 macOS ARM64 Release CLI；没有构建 iOS、启动模拟器或使用设备。`benchmarks/python_loop.py` 保持原样，SHA256 为 `736118e90c7989f0352d26bce340ef3118a4efcf7d6b465ba4a71a99849e5eec`，每次 checksum 均为 1267865。

## 计时范围与直接测量

两次 `time.perf_counter()` 只包围 100×100 像素、每像素三个源的原始 Python 循环；包含其 CPython 实现、客体 libm 及运行时执行、懒编译、校验的成本。导入、循环前初始化、打印、进程退出在外。此前四版本同场对照的当前版本循环为 2,014.697 ms、整个进程为 2,852.086 ms；两者之差不能全部叫作启动编译。

本轮原样生产二进制与边界诊断版交替运行，各先运行一次，再测五次；每次为新进程，预热不意味着保留上一进程的区域缓存。

各项中位数独立计算，不能当作同一次运行的完整轨迹。诊断版不同运行的循环为 1,943.732–2,068.380 ms，编译累计为 116.371–130.016 ms。诊断版与生产版的差异在本轮波动范围内，不能据此声称插桩无开销或插桩使程序更快。线程 CPU 时间与循环墙钟几乎相等，等待不是主要来源。

指令数是循环边界之间的计数差，不是此前整个进程约 3.4 亿条的统计。已链接命中与 `next` 是两类路径计数，不能当作独立区域数量；编译调用包括首次编译及重追踪等，不能称为相同代码反复重编译 11,238 次。

## 循环内栈采样及毫秒估算

使用未插桩的生产二进制和原始 Python 源码，开启已有 syscall trace 以定位两次客体 `clock_gettime(CLOCK_MONOTONIC)`。侦查日志确认两者之间没有其他客体 syscall。在第一次完成的 trace 行出现后启动 `/usr/bin/sample`，第二次出现时立即向采样器发送 SIGINT，使其生成部分报告。生产执行器未加逐 kernel 计时或计数。

当前版采五次，共 7,817 个主线程样本；采样下循环中位数 2,119.432 ms。互斥叶样本优先归入编译、校验及其子调用，再归入状态、访存、ALU、浮点、边界等类别；新加入的 vector memory、floating、floating_pair 核已纳入分类。每棵主线程树的叶样本合计均核对到根计数。

下面**除编译为诊断版累计实测外，其他毫秒均是采样估算，不是逐函数秒表结果**。将未采样生产版的 2,008.645 ms 减去实测编译 121.593 ms 后，按非编译样本分布分摊。这样做便于解释约 2 秒的预算，不证明生产版各模块存在这些精确时长。采样器挂接有延迟，会漏掉循环最前面的一小段，尾调用会隐藏前驱，采样本身也有扰动。

| 类别 | 循环内样本占比 | 各次占比范围 | 约 2,009 ms 预算中的毫秒 |
| --- | ---: | ---: | ---: |
| 客体数据访存执行核 | 26.10% | 23.60–27.99% | 约 523，估算 |
| GP 状态读入、写回、spill/reload | 17.26% | 15.39–18.43% | 约 346，估算 |
| 整数 ALU、常量执行核 | 14.60% | 12.81–16.17% | 约 292，估算 |
| 区域代码校验及子调用 | 13.50% | 12.40–13.86% | 约 270，估算 |
| 区域出口、分支、缓存解析 | 12.41% | 12.16–12.74% | 约 249，估算 |
| 区域编译 | 5.78% | 5.11–6.34% | 121.593，插桩累计实测 |
| FP/SIMD 执行核与语义实现 | 4.16% | 2.96–4.78% | 约 83，估算 |
| 其他运行时 / 宿主系统路径 | 3.58% | 2.68–3.99% | 约 72，估算 |
| 其他语义 helper | 2.62% | 2.39–2.84% | 约 53，估算 |

访存包含地址翻译、权限/驻留路径、TLB refill、实际读写及其中的子调用，不能把 523 ms 全叫作多余检查或复制。状态搬运是执行角色与客体 CPU 状态、临时槽之间的值传递，有直接采样支持。FP 类别没有涵盖一个 Python 浮点表达式的所有工作，更不是 `sin` 或 `sqrt` 的独立耗时。客体 CPython 与 libm 的整数、访存行为分散在多个执行核类别里，因此不能用这张表将“Python 本身”与“解释器额外开销”完全拆开。

## 已核实的重复校验来源

在另一组三次边界诊断中增加 epoch 观测，未加入逐 kernel 时钟。三次都满足：循环内 `run` 调用次数 = 代码 epoch 增量 = 相邻 `run` 之间 epoch 变化次数；`run` 内部 epoch 变化次数为零。

其中一次配对数据：

| 同一次运行的边界差 | 实测 |
| --- | ---: |
| 循环墙钟 | 1,960.866 ms |
| 线程 CPU | 1,959.352 ms |
| 客体指令 | 290,207,990 |
| `run` 调用 | 70,852 |
| 代码 epoch 增量 | 70,852 |
| 相邻 `run` 之间 epoch 变化 | 70,852 |
| `run` 内部 epoch 变化 | 0 |
| 区域校验调用 | 4,760,085 |
| 区域编译调用 | 11,303 |
| 区域编译累计 | 119.074 ms |

对应现有代码链路：

1. `runtime/machine.cpp` 在每次重新进入执行核前调用 `memory.synchronize_shared()`，执行预算受剩余时间片限制；时间片为 4,096 条客体指令。
2. `memory/mapping_operations.h:108` 的 `synchronize_shared()` 在存在文件映射时进入同步分支；存在可执行文件映射就推进全局 `code_epoch`，没有先判定代码字节真实改变。
3. `static_backend.cpp:499` 的链接出口要求目标区域的 `validated_epoch` 等于当前 `code_epoch`。时间片后的全局版本变化会令既有快速链接进入解析路径。
4. `region_engine.cpp:90` 发现版本不一致就调用区域校验。成功校验只更新这个区域的凭证，其他区域再次被访问时仍要补校验。
5. 因而每次时间片重新进入后，沿途多个区域都需要再次校验。该次约每个 `run` 对应 67 次校验；这解释了约 7 万次时间片入口如何放大为约 476 万次区域校验。

这是全局**验证凭证过期**，不能表述为每次都删掉机器码并重新编译。编译与校验是不同计数和成本。需要改的是失效范围与触发条件，而不能直接删掉对实际文件/代码变化的检测。

## 为什么循环没有获得预期优势

目前编译的是 AArch64 指令区域，不是将整段 Python 循环变成宿主原生循环。每区域最多取 128 条客体指令；运行时仍通过 24 字节记录连接静态 C++ kernel。区域出口写回/导出状态，下一区域重新导入工作值，`edge` 快速链接传入的八个工作角色也重新置零。这些状态传递在循环内部继续发生，并且全局 epoch 更新又不断阻断快速链接。

本轮估算的状态搬运、区域进出、代码校验，加上累计编译，合计约 987 ms，接近这 2 秒的一半。这个合计说明当前架构成本分布，不能等同于修改后可全部省掉的时间。访存执行核约 523 ms 还同时承担 CPython 实际数据操作及运行时寻址，仍需继续细分才能确定哪些步骤可消除。

因此下一步优先检查全局失效范围与区域之间的值衔接，再对真实访存路径作针对性优化。本轮没有实施这些修改，没有测得其可实现的节省。旧后端在此前四版本同场原始循环为 1,099.222 ms，当前 2,014.697 ms，仍有 915.475 ms 的差距；不能把已优化局部执行核等同于追回了整个差距。
